Meteor is translation-solution agnostic and bundles English and German snippets, so nothing
is required to get started — components render their bundled snippets out of the box.

Every component asks one question at runtime: _"which language should I show right now?"_
The setups below only differ in who answers it.

**Which setup do I need?** Two questions decide it: does your app have texts of its own,
and if so, what translates them?

| Your app                                                                                   | Setup                                                       |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| **Has no texts of its own** — bundled English/German is enough                             | Nothing — works out of the box                              |
| **Has no texts of its own** — but should follow the Shopware Admin's language (iframe app) | SDK locale recipe (below)                                   |
| **Has no texts of its own** — but needs another language or different Meteor wording       | `createMeteorI18nPlugin({ locale, messages })`              |
| **Translates its own texts with vue-i18n**                                                 | `createVueI18nAdapter(i18n)` — one locale drives everything |
| **Translates its own texts with another solution** (i18next, Tolgee, Paraglide, ...)       | Custom adapter `{ locale, t, n? }`                          |

## The Meteor i18n plugin

To switch language reactively or let your app provide/override translations, install the
Meteor i18n plugin with an optional host adapter:

```ts
import { createApp } from "vue";
import { createMeteorI18nPlugin } from "@shopware-ag/meteor-component-library";
import App from "./App.vue";

createApp(App).use(createMeteorI18nPlugin()).mount("#app");
```

Resolution order for every snippet: host adapter → plugin `messages` registry → Meteor's
bundled snippets → the key itself. The locale fallback chain is `de-DE` → `de` → `en`.

## vue-i18n

Already using `vue-i18n`? Connect it with the bundled adapter. Meteor then follows your
instance's locale and lets it override any snippet, falling back to its own snippets on a miss:

```ts
import { createApp } from "vue";
import { createI18n } from "vue-i18n";
import {
  createMeteorI18nPlugin,
  createVueI18nAdapter,
} from "@shopware-ag/meteor-component-library";
import App from "./App.vue";

const i18n = createI18n({ legacy: false });

createApp(App)
  .use(i18n)
  .use(createMeteorI18nPlugin({ adapter: createVueI18nAdapter(i18n) }))
  .mount("#app");
```

Notes on the vue-i18n adapter:

- Pass the **global** composer (`createI18n(...)` result, `i18n.global`, or a root-scope
  `useI18n()`); component-local composers are disposed when their component unmounts.
- `legacy: false` is **required** — the adapter reads a Composition-mode composer; in legacy
  mode `locale` is not a ref and language switches stop propagating (the adapter warns about
  this in development).
- Keys that exist only in your `fallbackLocale` catalog still resolve: the adapter probes the
  primary fallback explicitly, working around `te()` checking only the active locale on
  vue-i18n < 11.3.0. Only the primary fallback is probed — multi-level or locale-map
  `fallbackLocale` chains are not walked on those versions, so overrides living deeper in
  the chain silently fall through to Meteor's bundled snippets.
- A host override that fails to compile (unescaped special characters, see below) degrades
  to Meteor's bundled snippet with a development-mode warning instead of crashing the render.
- Hosts that carried snippet overrides for Meteor's pre-6.0 key names (`mt-field-error.*`,
  `mt-text-editor*.*`, `mt-action-menu-item.*`) can keep serving them during migration with
  `createVueI18nAdapter(i18n, { legacyKeys: true })` — each legacy hit logs a development-mode
  deprecation warning.
- Translations that are not statically visible to `te()` — flat dotted-key catalogs on
  vue-i18n < 11.3.0, or translations served at runtime through a `missing` handler
  (backend-driven catalogs) — need `createVueI18nAdapter(i18n, { skipExistenceCheck: true })`.
  The adapter then calls `t()` directly and treats a result identical to the key as a miss;
  costs are a full fallback traversal per miss and vue-i18n's missing-key warnings.

### Supported vue-i18n versions

- **Supported:** v9 and newer, Composition mode only (`legacy: false`; vue-i18n v8 is not
  supported). `petite-vue-i18n` works too — register overrides as literal dotted keys, its
  resolver is flat-only.
- **Recommended:** v11.4.9 or newer.
- **Known problem versions:**
  - **< 11.3.0** — `te()` misses dotted keys stored in _flat_ catalogs
    ([intlify/vue-i18n#2375](https://github.com/intlify/vue-i18n/issues/2375)), so `mt.*`
    overrides registered flat are silently discarded. Use nested catalogs, `flatJson: true`,
    `skipExistenceCheck: true`, or upgrade.
  - **11.3.0 – 11.4.8** — the fallback-locale chain is cached and ignores runtime mutations
    of `fallbackLocale` ([intlify/vue-i18n#2562](https://github.com/intlify/vue-i18n/issues/2562),
    fixed in 11.4.9), which can make `te()` answer for a stale locale set.
  - **v12** — currently in alpha; untested until stable.

### Interop notes for vue-i18n hosts

- Special characters `{` `}` `@` `$` `|` in override strings placed in **your vue-i18n
  catalog** need vue-i18n's escapes (literal interpolation like `{'@'}`, or `\@`-style escape
  sequences since 11.3). The same string placed in Meteor's plugin `messages` registry needs
  no escaping — Meteor's own renderer has no message compiler.
- A global `postTranslation` hook runs on adapter **hits** only (Meteor's registry and
  bundled snippets bypass it), and it will see `mt.*` keys it has never registered.
- `escapeParameter: true` HTML-escapes interpolated values; Meteor renders snippets as plain
  text, so escaped values show up as literal entities. Prefer keeping Meteor overrides free of
  values that need HTML escaping.

## Iframe apps (Admin SDK)

Inside an iframe, the Admin SDK is the only place the host admin's language can come from —
something has to carry that answer to Meteor.

**The recommended default for apps** is the vue-i18n setup: almost every app has at least a
few texts of its own (card titles, button labels), and one vue-i18n instance then drives both
the app's texts and Meteor's. Drive its locale from the Admin SDK — one locale source for
everything:

```ts
import { context } from "@shopware-ag/meteor-admin-sdk";
import { createI18n } from "vue-i18n";
import {
  createMeteorI18nPlugin,
  createVueI18nAdapter,
} from "@shopware-ag/meteor-component-library";

const { locale, fallbackLocale } = await context.getLocale();

const i18n = createI18n({
  legacy: false,
  locale,
  fallbackLocale,
  messages: appMessages,
});

void context.subscribeLocale(
  ({ locale: nextLocale, fallbackLocale: nextFallbackLocale }) => {
    i18n.global.locale.value = nextLocale;
    i18n.global.fallbackLocale.value = nextFallbackLocale;
  },
);

app.use(i18n);
app.use(createMeteorI18nPlugin({ adapter: createVueI18nAdapter(i18n) }));
```

**The rare case — no texts of your own at all** (a widget or service whose visible text is
entirely Meteor's): you don't need an i18n framework, just a hand-written adapter that tells
Meteor which language the admin is on. This doubles as the reference for how small an adapter
is:

```ts
import { createApp, ref } from "vue";
import { context } from "@shopware-ag/meteor-admin-sdk";
import { createMeteorI18nPlugin } from "@shopware-ag/meteor-component-library";
import App from "./App.vue";

// Await the initial locale BEFORE mounting — a .then() wiring would flash English.
const { locale: initialLocale } = await context.getLocale();
const locale = ref(initialLocale);

// Keep following the admin's language switches.
void context.subscribeLocale(({ locale: nextLocale }) => {
  locale.value = nextLocale;
});

const app = createApp(App);

app.use(
  createMeteorI18nPlugin({
    adapter: {
      locale,
      // Never translates anything itself (always returns undefined), so Meteor falls
      // back to its own bundled en/de texts — this adapter only tells Meteor which
      // language the admin is on.
      t: () => undefined,
    },
  }),
);

app.mount("#app");
```

When your app grows its own texts, keep this `locale` ref and hand it to vue-i18n (then
switch the adapter to `createVueI18nAdapter(i18n)`) or to your own small dictionary —
nothing gets thrown away.

## Custom adapters

Any other solution works by providing your own adapter (`{ locale, t, n? }`):

- `locale` is a reactive source (`Ref`, computed, or getter) of the host's current locale.
- `t` returns the translated string on a hit and `undefined`/`null` on a miss — never the key —
  so Meteor can fall back to its bundled snippets. On a hit, `t` must read your reactive locale
  _inside_ the call (e.g. `t: (key) => catalogs[locale.value]?.[key]`), otherwise components
  won't re-render on language switches. Solutions without reactive state (e.g. i18next) need a
  ref you update from their change event (`i18next.on("languageChanged", ...)`).
- `n` is optional locale-aware number formatting; without it Meteor uses `Intl.NumberFormat`.

### Tolgee

A locale-only adapter is all a [Tolgee](https://tolgee.io/) host needs — Meteor's snippets
translate themselves, and overrides go through the plugin `messages` registry:

```ts
import { ref } from "vue";

const locale = ref(tolgee.getLanguage() ?? "en");
tolgee.on("language", (event) => {
  locale.value = event.value;
});

app.use(createMeteorI18nPlugin({ adapter: { locale, t: () => undefined } }));
```

The `language` event fires after the language's data has loaded, so there is no flash of
untranslated content. We recommend against routing Meteor keys through `tolgee.t()`: with
in-context editing active, Tolgee embeds invisible marker characters into translated strings,
which corrupts attribute values like `aria-label` — and the adapter contract cannot know
where a string will land.

### Paraglide JS

[Paraglide](https://inlang.com/m/gerre34r/library-inlang-paraglideJs) compiles messages to
per-message functions, so there is no dynamic key lookup to adapt — which is fine: a
locale-only adapter plus the registry covers Meteor.

```ts
import { getLocale, baseLocale } from "./paraglide/runtime.js";

app.use(
  createMeteorI18nPlugin({
    adapter: {
      // getLocale() throws when no strategy resolves a locale — guard it.
      locale: () => {
        try {
          return getLocale();
        } catch {
          return baseLocale;
        }
      },
      t: () => undefined,
    },
  }),
);
```

Paraglide's default locale switch navigates/reloads the document, so a plain getter is
sufficient. If you switch with `setLocale(locale, { reload: false })` (SPA mode), bridge the
locale into a ref via `defineCustomClientStrategy` and pass that ref instead.

## Translating & overriding Meteor snippets

Every Meteor snippet has a public key of the form `mt.<component>.<key>` — e.g.
`mt.pagination.nextPage`, `mt.data-table.itemsPerPage`, `mt.field-error.INVALID_MAIL`. There are
two ways to override Meteor's wording or add a language it doesn't bundle:

**1. Via the host (recommended in the Shopware Admin).** Because resolution is host-first, a
snippet registered in the host's translation system under the `mt.*` key wins. In the Admin this
means a plugin translates a Meteor snippet exactly like any other admin snippet — add it to your
`en-GB.json` / `de-DE.json` and register it the usual way:

```json
{ "mt": { "pagination": { "nextPage": "Weiter" } } }
```

**2. Via the plugin registry (standalone apps).** Pass `messages` to override snippets or add
locales without a host translation system. Keys are the full public `mt.*` keys; locales are the
codes your app uses (region-specific overrides fall back to the language, then English):

```ts
app.use(
  createMeteorI18nPlugin({
    messages: {
      fr: {
        "mt.pagination.nextPage": "Suivant",
        "mt.pagination.previousPage": "Précédent",
      },
      "en-US": {
        "mt.pagination.nextPage": "Next",
      },
    },
  }),
);
```

Keys can be written flat (as above) or as nested objects — both resolve.

Meteor bundles `en`/`de`; any unsupported locale falls back to English unless you supply it here
(or via the host). Further languages are intentionally **not** bundled — add them through the
registry or your host, never by inlining catalogs into components.

Two caveats when writing your own message strings:

- **Pluralization** uses vue-i18n's pipe syntax (`"one item | {n} items"`) with the default
  English/German rule. Languages with other plural systems (Russian, Polish, Arabic, ...) should
  be served through a host adapter whose translation solution implements their plural rules —
  the registry applies the Latin rule to every locale.
- Snippet values are inserted as plain text. Never render a `t()` result with `v-html` —
  interpolated values are not HTML-escaped.

## Inside Meteor components

Meteor's own components translate their texts with the exported
[`useMeteorI18n` composable](/utilities/composables/use-meteor-i18n) — use it if you build
custom components that should translate the same way.
